DGX Spark Demo: Operator Guide

How to get on the box, issue a customer key, run a demo, and fix the five things that actually go wrong. One NVIDIA DGX Spark (GB10, 128 GB unified), hostname edgexpert-2316, Ubuntu 24.04, in the LocalAI Thailand office.

Not linked from anywhere and not indexed, but it is a public URL. It contains no keys and must stay that way.

Access

1. Join the tailnet

The owner invites you at login.tailscale.com (Users → invite) and adds an SSH rule for you under Access Controls. Install Tailscale on your laptop, sign in with the invited account, and the Spark appears as node edgexpert-2316 at 100.75.76.59.

2. SSH

ssh localaithai@edgexpert-2316

Tailscale SSH: no key to copy, no password to type. Your tailnet identity is the credential. If it asks for a password, your SSH rule is missing — ask the owner, do not work around it.

3. The endpoints

Public
https://spark.dgxthai.com/v1 — what customers get
Anthropic format
https://spark.dgxthai.com/v1/messages
Admin UI
https://spark.dgxthai.com/ui — log in with your own admin account. Owner and partner each have one; the master key does not open the UI.
Private (on tailnet)
http://edgexpert-2316:4000/v1 with the master key — skips Cloudflare, no 100s timeout
Master key
~/spark-demo/master_key on the Spark. It exists nowhere else.

The master key is admin. It mints and revokes every customer key over the API. Never put it in a message, a ticket, a slide, or a customer's config. Customers get virtual keys, always. The admin UI is a separate login — your own account, not the master key.

Issuing a customer key

ssh localaithai@edgexpert-2316
cd ~/spark-demo
./keys.sh new acme 7d     # prints the key ONCE
./keys.sh list            # alias, hashed token, expiry
./keys.sh revoke acme     # after the demo; also accepts an sk- key

Use the customer's company as the alias. 7d is the default and the right answer for a demo.

keys.sh list can only show a hash — LiteLLM stores a SHA-256 of each key and never the key itself. Lost the plaintext? Revoke the alias and issue a new one. There is no recovery.

The admin UI at /ui does the same thing with a form — sign in with your own admin account, then Virtual Keys → Create New Key, set an alias and an expiry. Same result; the CLI is faster.

No spend limits. Ollama costs nothing per token, so a budget is meaningless here. Expiry and revoke are the controls.

Demo-day checklist

  1. Check what is loaded. ollama ps over SSH. You want the tier-1 model listed.
  2. Warm it. Send one real request (curl below, or the admin UI's test playground) and wait for it to finish. A cold tier-1 load is about 20 seconds — spend them now, not in front of the customer.
  3. Create the key. ./keys.sh new <customer> 7d. Copy the output immediately; it prints once.
  4. Send the customer the link to localaithai.com/spark/customer.html and the key, in separate messages.
  5. Revoke when the demo is over. ./keys.sh revoke <customer>. Do not rely on the 7-day expiry to tidy up for you.
curl -s http://edgexpert-2316:4000/v1/chat/completions \
  -H "Authorization: Bearer $(ssh localaithai@edgexpert-2316 cat spark-demo/master_key)" \
  -H 'Content-Type: application/json' \
  -d '{"model":"claude-spark","messages":[{"role":"user","content":"warm up"}]}'

Model management

ollama list            # everything on disk
ollama ps              # what is resident in memory right now
ollama pull <tag>      # add a model (slow: tier 1 is ~95GB)

Three models are configured. Only tier 1, or tiers 2 and 3 together, fit in memory at once — Ollama swaps on demand and the first request after a swap costs about 20 seconds.

Pulling a model is not enough to expose it: the gateway config is generated from the MODELS list, so after a pull the owner reruns setup.sh with the new tag included. Ask; do not hand-edit litellm_config.yaml, the next rerun overwrites it.

Troubleshooting

SymptomCheckFix
Customer gets 401 ./keys.sh list — is the alias there, and is the expiry in the future? Expired or revoked: issue a new key. Present and valid: they are sending the wrong header or pasted a truncated key.
First request hangs ~20s, then works ollama ps Nothing to fix. That is the model loading. Warm it before a demo.
URL dead / connection refused from outside systemctl status cloudflared, then journalctl -u cloudflared -n 50 sudo systemctl restart cloudflared. Still dead: the Spark's internet is down — check from the tailnet URL to confirm the box itself is fine.
Long answers cut off around 100 seconds Is the request going through spark.dgxthai.com? Cloudflare's proxy timeout. Ask for shorter replies, stream, or use the tailnet URL http://edgexpert-2316:4000/v1 for your own testing.
Gateway answers but every model errors sudo docker compose -f ~/spark-demo/docker-compose.yml logs litellm and journalctl -u ollama -n 50 Ollama is down or mid-pull. sudo systemctl status ollama. If a pull is running, wait — see below.

Everything is a systemd or Docker service and comes back by itself after a reboot. If the whole box was restarted, give it a couple of minutes before concluding anything is broken.

Do not

Never delete Ollama's *-partial* files by hand. They are resume markers, not junk. Removing them makes the finalize step fail and silently truncates the blob — you then have a model that looks present and does not work. If a download is genuinely broken, remove the whole model and pull it again.

Never restart Ollama during a pull. It kills the download and corrupts the resume state. Tier 1 is a 95 GB pull; losing it costs hours.

  • Do not hand out the master key, ever.
  • Do not hand-edit litellm_config.yaml — the next setup.sh rerun regenerates it.
  • Do not point a customer at the tailnet URL. It requires the master key.
  • Do not run setup.sh yourself while a pull is in flight. Owner territory.
