Architecture

  • LiteLLM owns authentication. Ollama has none. Anything that can reach :11434 directly is unauthenticated, which is why it binds to 127.0.0.1.
  • Postgres holds key hashes only. Plaintext keys exist once, in the output of keys.sh new.
  • Tailscale bypasses Cloudflare entirely, so it has no 100-second response cap. Use it for long test runs.

Access

Partner onboarding: invite at login.tailscale.com (Users → invite), then add an SSH rule for them under Access Controls. They install Tailscale and get in with:

Tailscale SSH — no key exchange, no password. Revoking the tailnet user removes the access.

Admin UI: https://spark.dgxthai.com/ui. Owner and partner each sign in with their own admin account; the master key does not open the UI. It remains the API credential for keys.sh and for the private tailnet endpoint.

Issuing customer keys

cd ~/spark-demo
./keys.sh new acme 7d     # prints the key ONCE
./keys.sh list            # alias, hashed token, expiry
./keys.sh revoke acme     # also accepts an sk- key

Or the admin UI, signed in as yourself: Virtual Keys → Create New Key. Same object either way.

From a laptop instead of the box:

export SPARK_URL=https://spark.dgxthai.com
export LITELLM_MASTER_KEY=sk-...
./keys.sh list

Budgets are pointless here — Ollama has no per-token cost. Expiry and revoke are the only real controls.

Demo-day checklist

  1. ollama ps — confirm the tier-1 model is resident.
  2. Warm it with one real request and let it finish (~20s cold).
  3. ./keys.sh new <customer> 7d and copy the output at once.
  4. Send the customer page and the key in separate messages.
  5. ./keys.sh revoke <customer> when the demo is over.

The setup.sh rerun contract

ssh -t localaithai-xp1 'sudo -v && TUNNEL_HOST=spark.dgxthai.com bash ~/spark-demo/setup.sh'

This is the one command that changes the box. Rerun it after any change. What it guarantees:

  • Idempotent. Safe to run repeatedly.
  • Keys survive. They live in Postgres; the master key and the Postgres password are generated once into ~/spark-demo/ and reused.
  • The URL survives as long as TUNNEL_HOST is passed. Drop it and you fall back to a throwaway *.trycloudflare.com host — do not do that here.
  • Ollama is only restarted if its systemd drop-in actually changed. This is deliberate; see the incident log.
  • litellm_config.yaml is regenerated from MODELS every run, so the gateway always matches what is pulled. Never hand-edit it.
  • LiteLLM is explicitly restarted each run, because compose up -d does not notice a bind-mounted config change.
  • It self-checks before declaring READY: 401 unauthenticated, 200 with the master key, and a real completion on a freshly minted virtual key. A failure is a non-zero exit, not a warning.

DNS, Cloudflare and the tunnel

  • dgxthai.com is on Cloudflare DNS, free plan. That is all the plan needs to do.
  • spark is a proxied CNAME to the named tunnel spark; the target is <uuid>.cfargotunnel.com, and the UUID is in ~/.cloudflared/config.yml on the Spark.
  • cloudflared tunnel login ran once and wrote ~/.cloudflared/cert.pem. Without it, setup.sh refuses the named-tunnel path rather than silently degrading.
  • cloudflared service install put the unit in systemd and copied the config to /etc/cloudflared/config.yml; a rerun copies the config again but does not reinstall the service (it is not idempotent and aborts on a conflicting configuration).
  • TLS terminates at the Cloudflare edge. Nothing on the Spark holds a certificate and no inbound port is open.
  • Repointing to a different hostname is a rerun with a different TUNNEL_HOST. Nothing else moves.

Known limits

  • Office upload bandwidth is the ceiling, not the GPU. Every token leaves through the office link.
  • 2–3 concurrent users is fine. 20 is not. Ollama queues FIFO with no continuous batching.
  • Cloudflare caps a proxied response at 100 seconds. Long single generations get cut. The tailnet URL has no such cap.
  • No per-token cost, so budgets are theatre. Expiry plus revoke is the control surface.
  • Keys live in Postgres on the box with no backup. A rerun recreates nothing. Losing the box means re-issuing every key.
  • 64K context per request, 2 parallel slots, q8 KV cache (OLLAMA_CONTEXT_LENGTH=65536, OLLAMA_FLASH_ATTENTION=1, OLLAMA_KV_CACHE_TYPE=q8_0, OLLAMA_NUM_PARALLEL=2), one setting for all models, even though tier 1 can do 256K.

Do not

Never delete Ollama's *-partial* files by hand — they are resume markers. Removing them makes finalize fail and truncates the blob. Wipe the model and re-pull instead.

Never restart Ollama during a pull. It kills the download and corrupts the resume state.

  • Never hand out the master key.
  • Never hand-edit litellm_config.yaml; the next rerun regenerates it.
  • Never point a customer at the tailnet URL.

Incident log

2026-09-15 — setup.sh restarted Ollama and killed a 95 GB pull

What happened. A rerun of setup.sh wrote the systemd drop-in and restarted Ollama unconditionally. A tier-1 pull was in flight. The restart killed the download and left its resume markers inconsistent, so the retry could not continue from where it stopped.

Why. The script treated "write the config" and "restart the service" as one step, with no test for whether the config had actually changed. On a rerun it usually had not.

Fix, now in setup.sh. The drop-in is written to a temp file and compared with cmp -s against the installed one. Identical → systemctl enable --now only. Different → install, daemon-reload, restart. A rerun during a pull is now harmless.

Rule. Never restart a service to apply a config that did not change.

2026-09-16 — hand-deleting *-partial-N markers truncated the blob

What happened. After the failed pull, the *-partial-N files in the Ollama blob directory looked like leftover garbage and were deleted by hand to force a clean restart. The re-pull appeared to run, then failed at the finalize step, and what landed on disk was a truncated blob that still presented as a downloaded model.

Why. Those files are not junk. Ollama chunks a download and uses the partial markers to track which chunks are complete; finalize reassembles from them. Deleting them mid-flight destroys the accounting, and the failure surfaces at the end rather than at the point of damage.

Fix. Remove the model entirely and pull it again from nothing. Hours, not minutes, for tier 1.

Rule. Never touch *-partial*. If a download is bad, delete the whole model and re-pull. Both incidents were the same mistake in different clothes: interfering with a long download instead of leaving it alone.

2026-09-16 — old context window truncated agent prompts

The previous window truncated Claude Code/Codex prompts (Ollama log n_tokens = 32767, truncated = 1); raised to 64K + compaction flag.
